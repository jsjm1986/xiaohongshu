# 修改任务异步化与进度反馈

日期:2026-07-27
状态:已批准,待实施

## 问题

工作台侧边栏「继续调整当前候选」(revise)发起修改后,界面上只有一个转圈的按钮:没有进度条、没有阶段说明、没有完成提示。用户无法判断是在跑、跑到哪、还要多久。

探查后发现表层的反馈缺失只是症状,底层是机制问题。

### revise 与首次生成是两套机制

首次生成走队列:`generation_jobs.status`/`progress` 落库,前端轮询,有 12→28→44→88→100 的真实里程碑,配套心跳、孤儿回收、多实例原子认领(`job-claim.ts`)。

revise 是**同步请求-响应**(`generation.service.ts:632` 的 `async revise()`),整个执行过程不落任何中间状态。前端 `handleRevise` 只有一个 `revising` 布尔量(`GenerationResultPage.tsx:77`),所以除了转圈没有别的可显示。

### 同步长请求在公网下不成立

revise 耗时是分钟级。实测线上两次 `revised` 事件相隔 299 秒;首次生成基线 3.6–25 分钟(库内完成任务实测 219s–1518s)。

隧道日志里已经出现过一次掐断:

```
2026-07-27T14:21:42Z ERR Request failed error="Incoming request ended abruptly: context canceled"
  dest=https://xhsai.maycran.com/api/generations/879a59f5-.../revise
```

Cloudflare 的 ~100 秒超时切断了连接。这与本仓库先前记录的分析端点 524 是同一类问题。

### 掐断后的行为是错的

连接被切,浏览器落进 `handleRevise` 的 `catch`(`GenerationResultPage.tsx:207-225`),该分支会:

1. 把用户的修改指令**追加到正文末尾**(`body: ${candidate.body}\n\n【修改说明】${revision}`)
2. 提示「演示模式:修改说明已记录」

用户会以为改好了,实际拿到一份被污染的正文。同时服务端那次请求已经扣了配额、可能还在继续跑。这是本次最该消掉的行为。

### 附带的记账问题

配额在调用模型前扣(`generation.service.ts:645`),失败不退。而分析任务遇到模型 5xx 是退还的(`intelligence.service.ts:1667`),提示语明确写「已退还本次额度」。两处行为不一致。

## 方案

revise 从同步请求-响应改成**异步队列任务**,复用已实测的认领/心跳/回收机制,走独立的表、独立的执行函数、独立的状态字段。

### 数据模型:独立表 `revision_tasks`

迁移 v15(`SCHEMA_VERSION` 14 → 15)。`generation_jobs` **一列都不加**。

```
revision_tasks
  id                    TEXT PRIMARY KEY
  job_id                TEXT NOT NULL REFERENCES generation_jobs(id) ON DELETE CASCADE
  package_id            TEXT NOT NULL   -- 解析后的 content_packages.id,执行时的权威目标
  candidate_id          TEXT NOT NULL   -- 用户点的原始标识,仅供追溯与前端匹配
  instruction           TEXT NOT NULL
  status                TEXT NOT NULL   -- queued | running | completed | failed
  progress              INTEGER NOT NULL DEFAULT 0
  attempt_count         INTEGER NOT NULL DEFAULT 0
  error                 TEXT
  rerun_channels_json   TEXT NOT NULL DEFAULT '[]'
  result_package_id     TEXT
  created_by            TEXT NOT NULL REFERENCES users(id)
  created_at            TEXT NOT NULL
  updated_at            TEXT NOT NULL
  completed_at          TEXT
  claimed_by            TEXT
  heartbeat_at          TEXT
```

形状仿 `analysis_tasks`——它是本仓库里异步任务的既有正确形状,经过实测(含孤儿判定修复)。

**两个 id 列的分工。** 现有实现按 `content.candidateId === candidateId || content.id === candidateId` 双条件查找(`generation.service.ts:639`),也就是前端传来的标识可能是两者之一。入队时**一次性解析成确定的 `content_packages.id` 存进 `package_id`**,执行阶段只认它;`candidate_id` 保留用户传入的原值,供追溯与前端匹配活跃任务。这样解析歧义只在入队时发生一次,执行路径没有二义性。若解析不到,入队即报 404,不进队列、不扣配额。

**为什么是独立表,不是给 `generation_jobs` 加列。** `revision_status` / `revision_progress` / `revision_request` 描述的是**一次修改动作**,不是 job 的属性。一个 job 会被改 N 次,单组列只记得住最后一次,历史修改的进度、失败原因、耗时全部丢失。且 `status` 与 `revision_status` 并存会让所有读 job 状态的代码都要先问"你说的哪个状态"。

**`generation_jobs.status` 保持 `completed` 不变。** revise 期间旧产出确实还在库里、确实能看。前端有 10 处按 `status === 'completed'` 决定能否查看/导出(`BatchBoard.tsx` 2 处、`HistoryTab.tsx` 3 处等),改动 status 会让用户在改稿期间打不开自己的稿子。

索引:只建 `revision_tasks(job_id, created_at)` 和 `revision_tasks(status, heartbeat_at)`。两者都建在本次新建的表上,不涉及"索引里带后加列在旧库报 no such column"那个坑(v13/v14 各踩过一次)。

### 认领与回收:泛化 `job-claim.ts`,不复制实现

现有 `claimNextJob(db, instanceId, now)` 内部硬编码 `generation_jobs`。抽成按表参数化的形式,`generation_jobs` 与 `revision_tasks` 共用同一份认领/心跳/回收实现:

- 认领仍是单条 `UPDATE ... WHERE status='queued'` + `changes === 1`,靠 SQLite 单写者模型保证互斥
- 回收判定**只看 `heartbeat_at`,不看 `claimed_by`**:`instanceId` 含 pid,重启即换身份(v14 迁移注释记的教训)
- `attempt_count` 上限 3,与 `RESTART_INTERRUPTION_LIMIT` 及 `analysis_tasks` 一致;触顶置 `failed`,不再自动重跑

现有 `job-claim.test.ts` 的用例继续覆盖泛化后的实现,另补一组针对 `revision_tasks` 的。

`analysis_tasks` 目前是第三份独立实现。它能用,把它并进来属于无关重构,**不在本次范围**。

### 执行路径

`drainRevisions()` 与现有 `drainQueue()` 并列,由同一个 `reclaimAndDrain` 定时器驱动。领到任务后跑 `processRevision()`,内部调现有 `agent.revise()`。

**并发上限 2,独立于 `maxConcurrentJobs`。** 改稿是交互式操作、用户在等,不该被排队的批量生成挡住;反过来也不该让改稿占满名额饿死新生成。

**写库只在最后一步、在单个事务内完成。** 现有实现是 `UPDATE content_packages SET id=?, content_json=? WHERE id=?`(原地覆盖),异步化后若在写库阶段失败可能留下半个包。设计上失败则一个字节都不动。

### 进度语义

里程碑按 `agent.revise()` 的真实阶段划(读 `engine.ts:2575-2760`),不做均匀插值:

| progress | 阶段文案 | 真实工作 |
|---|---|---|
| 0 | 排队等待中 | 未认领 |
| 10 | 分析修改影响范围 | `analyzeRevisionDependencies` 判定 rerunChannels |
| 25 | 载入知识与证据 | `loadKnowledge` + `hydratePlanningContext` |
| 40 | 重写受影响的环节 | 第 1 次模型调用(重写补丁) |
| 70 | 证据锚定复核 | 第 2 次模型调用,**条件触发** |
| 85 | 声明合规判定 | 第 3 次模型调用,**条件触发** |
| 95 | 质检与落库 | `validateGenerationDraft` + 写库 |
| 100 | 完成 | — |

70 与 85 只在机械锚定未命中时才发生(`engine.ts:2679`、`:2687`),所以进度可能从 40 直接跳到 95。这是真实情况,不为"平滑"而假装经过。

**新增 `revisionStageText()`,不复用 `progressStageText()`。** 后者的文案属于首次生成("解析选题"、"生成初稿"),套到 revise 上会说谎——revise 不解析选题、不生成初稿。两个纯函数,各自可独立测试。

**第一版不显示 ETA。** `wait-status.ts` 的 `SINGLE_ETA_SECONDS = [600, 1800]` 来自线上 55 篇实测;revise 目前只有 2 个样本,不足以定区间。只显示已等待时长与当前阶段,并在代码注释写明"样本不足,暂不给区间"。等库里积累够样本再补。

### 前端反馈

复用 `InlineProgress` 组件——它已有 `label='正在修改'` 的入口(`InlineProgress.tsx:10`),当初就为 revise 预留过。

侧边栏 `revision-box` 的三个状态:

- **修改中**:`InlineProgress` 显示阶段 + 已等待时长;按钮禁用,文案「修改中…」
- **完成**:toast「修改完成,已更新受影响的环节」并列出实际重跑的通道(取 `rerun_channels_json`);按钮恢复
- **失败**:toast 报明确原因;按钮恢复;**输入框保留原指令**(现在 `finally` 里无条件 `setRevision("")`,失败也清空,用户得重打一遍)

**删掉「演示模式」兜底**(`GenerationResultPage.tsx:207-225`)。异步化后失败就是失败,明确报错,绝不改动正文。

**轮询**:GET job 时带上该 job 的活跃 revision task,复用现有 job 轮询节奏。不新增独立轮询端点——多一个端点就多一处要处理认证、租户隔离与错误的地方。

### API 契约与三个调用方

`POST /api/generations/:id/revise` 从「同步返回改完的 job」变成「受理任务后立即返回」。返回体仍是 `GenerationJob`(不破坏类型),但附带该 job 的活跃 revision task 投影,并且此时 `candidates` 仍是**旧版本**。

revise 有三个调用方,不止工作台:

| 调用方 | 现状 | 异步化后 |
|---|---|---|
| `GenerationResultPage.tsx:204`(工作台侧边栏) | `await` 后直接 `setJob(next)`,失败走演示模式兜底 | 改为轮询 revision task,显示 `InlineProgress`;删掉兜底 |
| `quick-generation.ts:333`(极简创作) | **已经在轮询** `job.status === 'queued' \|\| 'running'` | 轮询条件改读 revision task 状态 |
| `QuickReaderPage.tsx:103`(阅读页) | `await` 后 toast「已按意见修改」 | 改为轮询;页面本身已有 3 秒轮询定时器可复用 |

**`quick-generation.ts` 那处是既有的隐性 bug。** 它的 `while (job.status === 'queued' || job.status === 'running')` 循环预期 revise 是异步的,但服务端同步返回时 job 已是 `completed`,所以那个循环体从未执行过,`maxPolls`/`GenerationStillRunningError` 全是死代码。异步化正好让这段代码开始按它本来的意图工作——但轮询条件要改成读 revision task,因为 `job.status` 在改稿期间保持 `completed`(见上文数据模型)。

三处都要改;漏掉任何一处的表现是"点了没反应、稍后自己变了"。

### 错误处理与配额

退还遵循与分析任务同一条原则:**只在确认无产出时退**。复用现有 `refundPlatformQuota()`(已有 `provider_mode !== 'platform'` 短路与 `MAX(0, ...)` 下限保护)。

| 失败类型 | 配额 | 理由 |
|---|---|---|
| 模型服务不可用(无响应/429/5xx/凭据异常) | 退还 | 用户什么都没拿到,不是他的问题 |
| 模型返回不合契约(JSON 坏、缺通道) | 退还 | 同上,重试通常就好 |
| 修改后校验不通过(硬门拒绝) | 不退 | 消耗了真实算力,产出了可判定的结果 |
| 指令非法(空、超长) | 不扣 | 在扣配额之前拒绝,不进队列 |

前两类的判定逻辑与 `intelligence.service.ts:157-174` 的 `analysisFailureException` 同构。**抽成共享 `model-failure.ts`,两处共用**,不写第三份——`intelligence.service.ts` 是第一份,再抄一遍就开始漂移。错误文案里的动作名由调用方传入("分析"/"修改")。

## 不变量与测试

每条都必须能在实现错误时变红:

1. revise 失败后 `content_packages` 字节不变,`generation_jobs.status` 仍为 `completed`
2. 模型 5xx → 配额退还;校验失败 → 不退
3. `kill -9` 后任务被回收重试,`attempt_count` 递增,触顶 3 次置 `failed`
4. 两实例并发时同一 revision task 只被领取一次
5. revise 期间 GET job 仍返回旧候选(用户能看旧稿)
6. `revision_tasks` 的任务不会被 `claimNextJob` 领走当成首次生成执行
7. 三个调用方各自都能等到修改完成:工作台、极简创作(`reviseAndPoll`)、阅读页

第 6 条对应探查阶段确认的真实风险:`claimNextJob` 只按 `status='queued'` 取,`drainQueue` 拿到 id 后直接调 `process()` 跑首次生成全流程,不看任务类型。若泛化后的认领实现串了表,后果是用全新的 3 个候选覆盖用户产出。必须有测试钉死。

## 不做

- 不并入 `analysis_tasks` 的第三份认领实现(能用,属无关重构)
- 不给 revise 显示 ETA 区间(样本不足)
- 不新增独立轮询端点
- 不改配额扣减时机(仍在调用模型前扣,只补退还)
