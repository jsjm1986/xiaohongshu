# 知识库补充闭环

## 问题

用户上传知识库、跑完分析、用 AI 补充之后,缺口仍然全部挂在「还要补什么」里,没有任何路径能真正关掉它们。实测某项目 18 条缺口:2 条有资料支撑、15 条仅人工确认、1 条空白,而 15 条「仅人工确认」在生成端拿不到证据,答案会被丢弃。

链路上有五处断点,都已在代码中核实:

**一、`sourceStatus` 没有传到前端。** `intelligence.service.ts` 的 `normalizeGap` 回传 14 个字段,不含 `sourceStatus`。而 `enrich-types.ts:79` 的 `gapStats` 与 `IntelligentSimpleFlow.tsx` 的 `isGapPending` 判据都读它,拿到的恒为 `undefined`。两处注释声称「与后端 pendingGaps 同一判据」,实际不一致——只是双方恰好都把「有答案」当已落实,才没有暴露。

**二、人工填答案不改变缺口状态。** 缺口编辑器填答案时只设 `answerability`,不设 `sourceStatus`。后端 `pendingGaps` 读 `data_json.sourceStatus`,分析写的 `unknown` 一直留着,于是人填完答案,缺口在池子里仍是「待补充」。

**三、`answerability` 写了没人读。** 编辑器把它写进 `data_json`,但 `normalizeGap` 不回传,`agent-core` 的 `InformationGap` 也没有这个字段。实测全库 331 条缺口**全部没有该值**——分析器从不产出它。

**四、AI 补充落成孤立文件。** `intelligence-enrich.service.ts:202` 的合并目标是 `targetFile ?? 找 INDEX.md ?? 'INDEX.md'`,而弹窗只回显后端算出的值,没有选择控件。实测:33.6 KB 的原始资料没被触碰,补充内容独立成 2.9 KB 的 `INDEX.md`(证据类型「猜想」)。

**五、「确认」能绕过重新分析。** `approveResource:2417` 只翻 status,不校验 `stale`。实测时间线:

```
18:29:45  分析完成
18:33:10  AI 补充存了 INDEX.md → markProjectStale → 分析变 stale
18:34:02  用户点「确认」 → 变回 approved,但没有重新分析
```

结果是缺口与 `evidenceId` 全部来自资料变动之前。用户看到的一屏「引用的证据已失效」正源于此。这一处是最严重的:不补它,任何待办提示都能被一次点击消掉。

## 决策

**缺口有三条关闭路径,人工确认与资料支撑同等有效。**

人工确认即可信——这是产品决策。实现上不依赖现有的自证副作用,而是走显式路径:`bindGapEvidence` 为人工确认的答案给出独立的证据 id。

理由:`planningEvidenceSupports`(`engine.ts:527`)把 `informationGaps` 自身序列化成证据源,所以人工答案本来会「自证」。但它格式敏感——JSON 转义会在换行、半角双引号、制表符、反斜杠处插入反斜杠,破坏子串匹配。实测 13 组对照:单行纯文本、中文标点、中文引号「」能自证;含换行、半角 `"`、制表符、反斜杠不能。而缺口编辑器的答案框是 `<textarea rows={3}>`,多行是常态。靠这个副作用等于让效力取决于用户有没有敲回车。

显式路径还保留了来源可追溯:证据台账里能区分「资料背书」与「人工背书」,而修归一化会让两者彻底混同。

**重新分析由用户手动触发,页面给常驻待办提示。**

分析是三段串联、三次模型调用、走额度。自动触发会让「补一条跑一次」变成浪费;只给 toast 提示则一闪就没,用户容易停在「存了但缺口还在」——那正是本次问题的现场。常驻待办条兼顾两者。

## 设计

### 数据流

```
① 上传资料 / 直接录入
        ↓  import → markProjectStale
② 分析(三段串联)→ 缺口带 answer / sourceStatus / evidenceIds
        ↓
③ 缺口三条关闭路径:
   ├─ 分析从资料里答出来        → supplied_fact  + 分节 evidenceId
   ├─ 人在缺口编辑器填答案并确认 → user_supplied  + evidence_human_approved
   └─ AI 补充存「猜想」          → 不关缺口,只整理出「该问什么」
        ↓
④ 资料写入让分析变 stale → 知识库页出现待办条
        ↓
⑤ 重新分析(仅资料变动时需要)→ 缺口带上新 evidenceId
        ↓
⑥ 确认分析 → 可以生成
```

三种归宿在台账里可区分:

| 关闭方式 | sourceStatus | 证据 id | 生成时 |
|---|---|---|---|
| 资料支撑 | `supplied_fact` | 分节 id | 采用 |
| 人工确认 | `user_supplied` | `evidence_human_approved` | 采用 |
| AI 补充 | `unknown` / `inference` | 无 | 不采用 |

AI 补充不关缺口——它存的是模型推测,没有人背书过。但它不再是死路:看完草稿,把认可的内容填进缺口答案并确认,那一刻就走了第二条路径。

失效的 `evidenceId` 由重新分析统一重建,不要求用户逐条重选。`evidenceId` 含 `documentId`(每版新 uuid),一次保存会让该文件所有引用同时失效,手工重选是错的指引。

### 改动清单

七处,按依赖排序。每处只做一件事。

**1. `normalizeGap` 补回 `sourceStatus`** — `apps/api/src/intelligence.service.ts`

纯增字段。前端判据生效的前提,必须先做。

**2. `sourceStatus` 增加 `user_supplied` 取值** — `apps/web/src/types.ts`

web 侧现有 4 个取值(`supplied_fact` / `inference` / `hypothesis` / `unknown`)扩到 5 个。字段存在 `data_json` 内,无 CHECK 约束,不需要迁移。

分析提示词**不**列出这个取值:它只能由人设置,模型不该自称人工确认。

**3. `agent-core` 新增 `sourceStatus` 字段与 `evidence_human_approved`** — `packages/agent-core/src/types.ts`、`engine.ts`

`agent-core` 当前**完全没有** `sourceStatus`(全仓 grep 零命中),`InformationGap` 也没有该字段。所以这一处要做两件事:

- `InformationGap` 增加 `sourceStatus?: "supplied_fact" | "user_supplied" | "inference" | "hypothesis" | "unknown"`,并由 api 的 `normalizeGap` 透传——即改动 1 的下游
- `bindGapEvidence` 的 `evidenceFor` 加第四条路径:`gap.sourceStatus === 'user_supplied'` 时给出 `HUMAN_APPROVED_EVIDENCE_ID`,与现有 `TASK_PROJECT_EVIDENCE_ID`、`PLANNING_CONTEXT_EVIDENCE_ID` 同一模式

这是本次核心。生成核心的回归面最大,改前先取 `agent-core` 全量基线。

**4. 缺口编辑器加「资料来源」控件** — `apps/web/src/pages/IntelligentSimpleFlow.tsx`

填答案时能设 `sourceStatus`。可选项只给人能合法声明的四种:

| 选项 | 值 | 含义 |
|---|---|---|
| 我确认过 | `user_supplied` | 默认。填了答案即选中,生成会采用 |
| 我的推断 | `inference` | 仍算待补充 |
| 假设 | `hypothesis` | 仍算待补充 |
| 还不确定 | `unknown` | 仍算待补充 |

`supplied_fact` **不可手选**——它表示「资料里有出处」,只能由分析器基于 `evidenceSections` 判定。若允许手选,用户会声称有资料支撑却拿不到任何 `evidenceId`(分节匹配不中,又因 `sourceStatus !== 'user_supplied'` 拿不到人工证据),答案在生成端照样被丢弃,等于造一个新的口径不一致。

清空答案时回落到 `unknown`,不保留 `user_supplied`——没有答案的「我确认过」是矛盾状态。

**5. `approveResource` 拒绝确认 stale 分析** — `apps/api/src/intelligence.service.ts`

只对 `project_intelligence` 生效,错误信息可操作:「资料已变动,请重新分析后再确认」。缺口、策略、选题的确认不受影响——它们的 stale 是分析级联下来的,重新分析会重建。

行为收紧:资料一改就必须重跑分析才能生成,不能再点「确认」跳过。用户已确认接受。

**6. 知识库页待办条** — `apps/web/src/pages/KnowledgePage.tsx`

`analysis === 'stale'` 时显示待办语气的提示并跳「内容生成」。复用现有 `needsAnalysis` 引导面板,只改文案。

**7. AI 补充保存后指向下一步** — `apps/web/src/components/knowledge/KnowledgeEnrichmentModal.tsx`

保存提示改为:草稿里认可的内容,去缺口池填进答案并确认。同时加目标文件选择器——API 早已支持 `targetFile`,默认值仍用后端算的值,但允许改成任一现有文件。修掉断点四。

### 明确不做

- **不修 `planningEvidenceSupports` 的格式敏感。** 显式路径让自证不再位于闭环主干。修它会让所有答案自证,等于废掉 `bindGapEvidence` 对 answer 的检查。
- **不建「补充批次」表。** `stale` 状态已是够用的触发信号,建表要付迁移与一致性成本,换来的精确条数用户不需要。
- **不动 AI 补充存「猜想」的降级。** 模型推测不该继承已知事实,这是刻意设计。
- **不把分析搬进知识库页。** 跨频道指路已足够;搬过来会让该页承载三段串联的进度与蓝图确认交互,过重。

### 测试策略

每处改动都要变异验证——改坏实现必须让测试变红。重点守三件事:

1. **人工确认的答案在生成端真的被采用。** 必须在 `agent-core` 层测 `bindGapEvidence`,不能只测前端:界面说采用而生成里被丢弃,正是本次要根治的失真。用例含多行答案、含半角双引号的答案——旧路径在这两种形态下会静默失败。
2. **`stale` 分析确实不能确认。** 覆盖 HTTP 层,并断言错误信息可操作。
3. **三种证据来源在台账里可区分。** 断言 `evidence_human_approved` 与分节 id 不混同。

改动 3 触及生成核心,先跑 `agent-core` 与 `apps/api` 全量取基线,再改。注意 `apps/api` 的测试会受 shell 环境变量影响:`ANTHROPIC_BASE_URL` 存在时 `cross-tenant-isolation` 的 BYOK 用例失败(`config.ts:211` 读它作 `platformBaseUrl`),不存在时 `generation-batch` 因缺模型网关挂起。取基线时要固定同一套环境。

### 风险

**改动 3 在生成核心。** `bindGapEvidence` 的输出进入 `gapPlanningCards`、`requiredOpenGap` 判定与覆盖台账。新增一条证据路径会让此前被丢弃的答案开始被采用——这是意图,但会改变既有项目的生成结果。合并前需在真实项目上验一次生成,确认正文没有出现新的失真。

**改动 5 会打断现有操作习惯。** 已获用户确认。

**工作树混杂。** 当前工作树有约 115 个未提交文件,其中约 101 个属于另一会话的在途工作,`knowledge.service.ts` / `api.ts` / `types.ts` 为双方共同修改。提交时需要处理归属,或等对方先提交。
