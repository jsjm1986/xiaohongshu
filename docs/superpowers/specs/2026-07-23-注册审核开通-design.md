# 注册申请 + 管理员审核开通 · 设计文档

- 日期:2026-07-23
- 状态:已获用户批准,待写实现计划

## 背景与目标

当前系统是"管理员开号"模式:没有自助注册,新账号只能由系统管理员在后台手工创建(`AuthService.createUser`)。产品需要开放**前端自助注册申请**:访客填写用户名、密码、机构名称、联系手机号提交申请,由管理员在后台**审核开通**。客服作为线下沟通渠道辅助,不是系统流程节点。

现有相关能力(复用,不重造):

- 认证:Argon2id 密码哈希 + 会话/CSRF + 登录限流(`auth.service.ts`)。
- 多租户:`users` / `workspaces` / `workspace_members` / `projects` / `project_acl`,5 角色 RBAC(`database.service.ts`、`guards.ts`)。
- 管理后台:`AdminController`(仅系统管理员)+ 前端 `TeamPage`。
- 审计日志:`AuditService`。
- 迁移机制:`PRAGMA user_version` 递增迁移,当前最新版本 v9,本功能挂 v10。

## 整体流程

```
访客填注册表 → POST /api/register(公开接口)→ 写入 registration_requests(status=pending)
   → 管理员在后台"注册申请"列表看到待审核项
       → 通过:事务内创建 user(用申请里已哈希的密码)+ 专属 workspace(机构名命名)
                + workspace_members(Owner);申请置 approved;记审计
       → 拒绝:填原因;申请置 rejected,存 review_note;记审计
```

登录时按用户名关联申请状态给出对应提示(审核中 / 未通过 + 原因)。

## 用户端设计

### 1. 登录页入口(`LoginPage.tsx`)

在 `.login-help` 附近加一行:"还没有账号?申请开通 →",链接到 `/register`。

### 2. 注册申请页(新页面 `/register`)

公开路由(不经 `ProtectedRoute`),字段:

| 字段 | 校验 |
|------|------|
| 用户名 username | 3–64 字符,`/^[^\s/\\]+$/`(沿用 `createUser` 规则) |
| 密码 password | ≥12 且 ≤256 字符(沿用 `validatePassword`) |
| 确认密码 | 前端校验与 password 一致 |
| 机构名称 organizationName | 必填,≤120 字符 |
| 联系手机号 phone | 中国大陆手机号 `/^1[3-9]\d{9}$/` |

提交成功 → 显示"申请已提交,审核中",并提供客服联系入口。用户此时不能登录。

**客服联系交互(有设计感的处理):**
- 客服微信号 `wjyy5035` 作为前端常量,**不以明文渲染**在页面上 —— 只呈现一个"复制客服微信"按钮。
- 点击按钮 → `navigator.clipboard.writeText('wjyy5035')` 写入剪贴板 → toast 提示"客服微信已复制,去微信添加即可"。
- 微信号存在于代码常量与剪贴板中,视觉上不裸露文本,避免页面出现一串账号显得廉价。
- 剪贴板 API 不可用时(非安全上下文/旧浏览器)的降级:按钮改为点击后短暂显示明文供手动复制。

### 3. 待审核期间登录提示

用户用申请中的用户名尝试登录时:
- 该用户名尚无正式账号,但有 pending 申请 → 提示"你的申请正在审核中,请耐心等待"。
- 有 rejected 申请 → 提示"申请未通过:{review_note}"。

实现方式:登录接口在用户名查不到 users 记录时,回查 registration_requests 给出对应状态提示(不泄露是否存在正式账号的安全边界:仅对 pending/rejected 申请给提示,其余仍返回通用"用户名或密码错误")。

## 管理后台设计

在 `TeamPage.tsx` 新增"注册申请"区块(仅 `isSystemAdmin` 可见),列出 pending 申请:机构名、用户名、手机号、申请时间。每条两个操作:

- **通过** → `POST /api/admin/registrations/:id/approve`。
- **拒绝** → 弹窗填原因 → `POST /api/admin/registrations/:id/reject`(body: `{ reason }`)。

审核结果记入审计日志(`action: registration.approve` / `registration.reject`)。

## 数据模型

新表(迁移 v10):

```sql
CREATE TABLE registration_requests (
  id TEXT PRIMARY KEY,
  username TEXT NOT NULL,
  password_hash TEXT NOT NULL,          -- 提交时即 argon2 哈希,不存明文
  organization_name TEXT NOT NULL,
  phone TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'pending'
    CHECK(status IN ('pending','approved','rejected')),
  review_note TEXT,                     -- 拒绝原因
  reviewed_by TEXT REFERENCES users(id),
  reviewed_at TEXT,
  created_user_id TEXT REFERENCES users(id),  -- 通过后指向创建的账号
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
CREATE INDEX registration_requests_status_idx ON registration_requests(status, created_at);
```

唯一性:提交时校验 username 未被正式用户占用、且无同名 pending 申请;phone 无 pending 申请。被拒绝后允许用同名重新申请(不做数据库级 UNIQUE 约束,靠提交时的应用层查询,以支持"拒绝后重申")。

## 接口设计

### 公开(无需登录,全系统唯一的公开写接口)

- `POST /api/register` — body `{ username, password, organizationName, phone }`。
  - 校验字段;查重(username 未被 users 占用 + 无 pending 同名/同手机号申请);argon2 哈希密码;插入 pending 申请。
  - **限流**:复用 `AuthService` 的失败计数机制思路,对注册接口按 IP/手机号做频率限制(如每 IP 每 15 分钟最多 N 次),防刷。
  - 返回 `{ ok: true }`,不回显任何敏感信息。

### 管理员(仅 systemRole=admin,挂在 `AdminController`)

- `GET /api/admin/registrations?status=pending` — 列出申请。
- `POST /api/admin/registrations/:id/approve` — 事务内:
  1. 再次校验 username 未被占用(防审核期间被人抢注)。
  2. `INSERT users`(system_role=user,**must_change_password=0**,因为密码是用户自己设的;password_hash 直接搬用申请里的哈希)。
  3. `INSERT workspaces`(slug 由机构名 slugify,owner_id=新用户)。
  4. `INSERT workspace_members`(role=Owner)。
  5. 申请 status=approved、created_user_id、reviewed_by、reviewed_at。
  6. 记审计。
- `POST /api/admin/registrations/:id/reject` — body `{ reason }`;status=rejected、review_note、reviewed_by、reviewed_at;记审计。

> 注:approve 复用 `AuthService` 里已有的建号/建工作区逻辑,抽出可复用方法,避免与 `ensureBootstrapAdmin` / `createUser` 逻辑重复。

## 错误处理

- 注册字段不合法 → 400,中文提示。
- username 已被占用 / 已有 pending 申请 → 409「该用户名已被使用或已提交申请」。
- 限流触发 → 429「申请过于频繁,请稍后再试」。
- approve 时 username 已被抢占 → 409,申请保持 pending,提示管理员。
- 非管理员访问审核接口 → 403(现有 guard 兜住)。

## 测试

后端单测(项目后端有测试框架):

- 注册提交成功 → 生成 pending 申请,密码为哈希非明文。
- 重复用户名 / 重复 pending 手机号 → 拒绝。
- 限流:超出阈值 → 429。
- approve → 正确创建 user + workspace + Owner 成员;申请状态流转;密码可直接登录(must_change_password=0)。
- reject → 状态与 review_note 正确。
- 拒绝后可用同名重新申请。
- 非管理员调审核接口 → 403。

前端:浏览器实测完整链路(注册 → 后台通过 → 新账号登录成功)。

## 明确不做(YAGNI)

- 邮箱验证、短信验证码、用户自助找回密码。
- 客服工单系统(客服为线下渠道)。
- 申请编辑 / 撤回。
