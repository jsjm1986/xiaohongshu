# 预检分档谎报修复:引用失效要说成引用失效

日期:2026-07-30

## 问题

知识库「还要补什么」面板把分析器的判定谎报成用户的手工确认。

实测某项目 18 条缺口,15 条落在 `approved_only` 档,界面对每一条都说:

> 答案没有对应的上传资料,依据是你填写并确认过。生成会采用,但它不是来自资料的事实。

而这些缺口的 `sourceStatus` 是 `supplied_fact` —— 分析器判定资料里有出处,用户从没手填过它们。这句话是假的。

### 根因

`classifyGap`(`apps/api/src/knowledge-preflight.ts`)分档只看「答案能否在当前资料里匹配到分节」,`sourceStatus` 根本没进 `PreflightGapInput`,结构上就读不到。匹配不中就一律归 `approved_only` 并套上「你填写并确认过」的说辞。

而这批缺口匹配不中的真实原因不是没有资料支撑,是**引用随资料的新版本整体失效了**:`evidenceId` 含 `documentId`,每个版本是新 uuid,所以一份资料存成新版本,指向旧版本的引用全部失效。实测该项目 `INDEX.md` 从 v1 存到 v2,同一次操作把分析打成 `stale`,并让 14 条缺口的引用同时断掉。

`approved_only` 于是同时装着两种完全不同的东西:真正的人工确认,和出处已断的分析器判定。仪表盘上那个「仅人工确认 15」是这个功能里最刺眼的一处失真。

### 一起被报告、但本次不修的第二个现象

AI 补充的默认目标固定是 `INDEX.md`(`intelligence-enrich.service.ts:203` 找不到就新建),所以用户那份 33 KB 的原始资料从没被并入过 —— 补充内容独立成一份「猜想」文件,与原始资料各自躺着。

它是**上面那个失效的成因之一**(存新版本 → 引用全断),但改默认反而会加重问题,详见 §4。本设计只修分档谎报。

## 设计

### 1. 新增一档 `evidence_stale`

`PreflightTier` 加第五档。`PreflightGapInput` 加可选 `sourceStatus`,取值沿用 `InformationGap.sourceStatus` 的五个成员。

`preflight()`(`knowledge.service.ts:436`)直接读 `data_json`,不经 `normalizeGap`,所以**读取处要自己过白名单**:库里实测有 5 行 `sourceStatus: 'unacknowledged'`,不在 `GAP_SOURCE_STATUSES`(`intelligence.service.ts:70`)之内。照 `:3461` 的写法,认不出的一律落 `undefined` —— 新档只认 `supplied_fact`,所以未知取值不会误入。

`classifyGap` 的分支顺序:

| 序 | 条件 | 档位 |
|---|---|---|
| 1 | 没有答案也没有 framework | `blank` |
| 2 | 当前资料能匹配到分节 | `evidence_backed` |
| 3 | `sourceStatus === 'supplied_fact'` **且** 有失效的声明引用 **且** `selfProofSurvives(答案)` | `evidence_stale` ← 新增 |
| 4 | `selfProofSurvives(答案)` | `approved_only` |
| 5 | 其余 | `will_be_dropped` |

**顺序是这次修复的核心。** 新分支必须在 `selfProofSurvives` 之前 —— 那 15 条都是单行答案,能通过自证,所以现在被第 4 条先截走了。同时必须在 `evidence_backed` 之后:引用虽失效但内容仍能匹配上的缺口,「有资料支撑」才是真实情况。

第 3 条的两个条件都必需:

- `sourceStatus === 'supplied_fact'` —— 分析器当初给过出处。
- 有失效的声明引用 —— 那个出处**确实断了**的实证。

只看前者会替一个可能已过时的判定作保:资料被整份删掉时,`supplied_fact` 这个上一轮的判定早已不成立,此时说「重新分析会重建引用」是空头承诺。要求 `staleDeclaredEvidenceIds` 非空,就把结论钉在当前可观测的事实上。该值 `classifyGap` 已经算好(对着项目可用证据全集 diff 声明的 `evidenceIds`),不需要新增输入。

第三个条件 `selfProofSurvives` 是审查发现后补的。没有它,格式会让答案在生成时真被丢弃的缺口(含换行/制表符/半角双引号/反斜杠)会先落进 `evidence_stale`,于是丢掉 `:126-129` 那几条逐字符的格式提示,还承诺「重新分析会重建引用」—— 而它的问题是格式,重新分析并不会修。加上这个条件,格式坏的一律留给 `will_be_dropped`。实测库里目前 0 行命中这种组合(210 条 `supplied_fact` 答案全是单行),所以这是潜在缺陷而非现存缺陷,但判据要一开始就对。

### 2. 文案

`evidence_stale` 的 `reasons` 首句:

> 原本有资料出处,但引用随资料的新版本失效了。重新分析会重建引用。

`classifyGap` 末尾那条既有的失效提示(「有 N 条引用的证据已失效…重新分析会一并更新」)对新档是同一件事说两遍,新档不再追加它;`approved_only` / `evidence_backed` 这些档位本身没提失效的,照旧追加。

前端 `knowledge-instrument.ts` 三张表各加一格:

| 表 | 值 |
|---|---|
| `TIER_LABEL` | 引用已失效 |
| `TIER_NOTE` | 出处随资料新版本失效,重新分析会重建 |
| `TIER_TONE` | `warn` |

用 `warn` 而非 `danger`:它可修复,且重新分析就能自愈,与 `blank` 同级。

### 2b. 前端还有三处必须一起改(审查发现,起初全漏了)

**`apps/web/src/lib/api.ts:234` 的 `PREFLIGHT_TIERS` —— 这一处是整个修复的成败点。**

它是运行时白名单数组,不是 `Record`,所以**不触发 typecheck**。不补新档,`preflightTier()`(`:236`)会把 `evidence_stale` 走 `:241` 的兜底、静默改判成 `will_be_dropped` —— 新档一条都到不了界面,而 `tiers.will_be_dropped` 被虚增。那句兜底注释(「认不出来的档一律当会被丢弃」)本身是对的设计,问题只在白名单没跟上。

同文件 `:274-279` 的 `tiers` 字面量是第 5 个需要补格子的 `Record`(这个会编译报错,漏不掉)。

**`apps/web/src/pages/KnowledgePage.tsx:381-420` 的仪表盘卡片是四段手写 JSX**,不是遍历。不补第五张,那 15 条缺口会从仪表盘**消失**,而让计数停止骗人正是本次的首要目标。新卡沿用同一 `V2InstrumentCell` 形状,图标用 `Link2Off`(lucide,已在依赖内)或复用 `TriangleAlert`,实施时确认导入。

**`actionableGaps` 的 `weight` 记录(`knowledge-instrument.ts:198`)** 决定待处理清单的排序,加成员会编译报错所以漏不掉,但**要明确排位**:`evidence_stale` 排在 `will_be_dropped` 之后、`approved_only` 之前 —— 它比「会被丢弃」轻(答案仍会被采用),比「仅人工确认」重(结论无法复核)。

三张表都是 `Record<KnowledgePreflightTier, …>`,联合类型加成员后漏格子会编译报错,所以补不全会被 typecheck 挡住。

### 3. 生成就绪度

`settled()` 是白名单(`evidence_backed || approved_only`),新档不加进去,自然计入 `requiredOpen`,`canGenerate` 随之为 false。`summarize` 里 `tiers` 那个 `Record<PreflightTier, number>` 需要补 `evidence_stale: 0`。

**理由不是「生成会丢弃它」——那是错的。** 我起初这么写,审查核实后推翻:`planningEvidenceSupports`(`engine.ts:565`)把 `planningContext.informationGaps` 整体序列化成证据源,缺口自己在里面,所以单行答案会自证并拿到 `PLANNING_CONTEXT_EVIDENCE_ID`,与 `sourceStatus`、与引用是否失效**都无关**。实测库里 210 条有答案的 `supplied_fact` 缺口全是单行、零个含换行或半角引号 —— 它们在生成端全都拿得到证据,不会被丢弃。

真实理由是**结论不可信**:引用失效意味着我们无法再验证这条答案确有资料出处。它在生成时会被采用(靠自证),但没有任何当前资料为它作证。让它挣住 `canGenerate`,是要求用户重新分析、重建一条可验证的引用链,而不是拿一个无法复核的答案去生成。这与 `will_be_dropped` 的理由不同(那一档是真的会被丢),但同样属于「不该就这么生成」。

**这一改动使模块头部与两处文案失准,须一并订正:**

- `knowledge-preflight.ts` 文件头「保守下界:显示站得住的一定站得住」—— 现在多了一档「站得住但无法复核」,措辞要覆盖它。
- `PREFLIGHT_NOTE`(同文件)同一句话,会随接口返回给前端显示。
- `summarize` 里 `requiredOpen` 那条注释提到「生成时正文会出现『关于 X 我还没问明白』」—— 对新档不成立(答案会被采用),需按档区分。

**`analysis` 与新档的组合必须两边都成立。** 我起初写「引用失效几乎总伴随 `analysis === 'stale'`」,审查用真实数据推翻:项目「眼袋王」`analysis` 为 `approved`、**零个知识文件**、49 条 `supplied_fact` 缺口 —— 所有引用必然失效,而分析已确认。此时 `preflightHeadline` 走 `!canGenerate` 分支(`knowledge-instrument.ts:157`),文案是「补上真实资料,或改掉会被丢弃的答案格式」、`needsAnalysis: false`、没有跳转按钮 —— 对引用失效这种情形是错的指引(改格式无用,要做的是重新分析)。

所以 `preflightHeadline` 的 `!canGenerate` 分支要按 `requiredOpen` 里的档位分情况:含 `evidence_stale` 时说「引用已失效,重新分析会重建」并给出跳转(`needsAnalysis: true`);否则保持现有文案。

### 4. 补充默认目标:撤回,不做

**本次不做。** 我起初设计成「前端默认选中最大的那份已知事实资料」,审查查出这会反过来制造本次要修的缺陷,已确认撤回。

`intelligence-enrich.service.ts:284` 在保存时**无条件**写 `evidenceStatus: '猜想'`(`ENRICHED_EVIDENCE_STATUS`)。所以默认并入用户那份唯一的事实资料,会:

1. 把它从「已知事实」降级成「猜想」——`knowledge-anchor.ts:100` 于是拒绝把它当事实锚点用于生成;
2. 存成新版本 → 新 `documentId` → 指向该文档的**所有** `evidenceId` 同时失效,正是本设计 §1 要修的那种失效;
3. 默认还非幂等:下次打开弹窗时该文件已是「猜想」,`defaultEnrichTarget` 找不到已知事实文件,回落空串 → 又写回 `INDEX.md`。

审查还查出两处实现层障碍(留档,将来做时会遇到):

- `knowledge_files.evidence_status` 库里真实存在 `approved` / `supplied_fact` 这类原始值,`api.ts:193-208` 把它们映射成「用户观点」而非「已知事实」—— 按「已知事实」字面挑,13 个有资料的项目里 5 个会静默落空。
- `ProjectKnowledgeTab.tsx:304` 传的是未折叠的 `knowledge.list` 行,「最大的已知事实」可能选到一个**最新版已是猜想**的文件名。

要真正解决「补充没并入原始资料」,前提是先让保存不降级目标文件(或把证据强度做到节级),那是独立一项,需单独评估。本设计只修分档谎报。

## 测试

`apps/api/test/knowledge-preflight.test.ts` 追加:

1. `supplied_fact` + 有失效引用 + 匹配不中 → `evidence_stale`,且 reasons **不含**「你填写并确认过」
2. `supplied_fact` + 无失效引用 + 匹配不中 → 仍 `approved_only`(作证条件生效)
3. `user_supplied` + 有失效引用 → 仍 `approved_only`(只认 `supplied_fact`)
4. `supplied_fact` + 有失效引用 + **能匹配上** → 仍 `evidence_backed`(顺序正确)
5. 必答的 `evidence_stale` → `canGenerate` 为 false
6. `supplied_fact` + 有失效引用 + 答案含换行 → 仍 `will_be_dropped`,且 reasons 保留逐字符格式提示(第三个条件生效)
7. `sourceStatus` 为 `'unacknowledged'`(库里真实存在的未知值)+ 有失效引用 → 不进新档

`apps/web/test/knowledge-instrument.test.ts` 追加:
- 三张 TIER 表都有新档的格子且文案非空;`evidence_stale` 的说明必须提到「重新分析」
- `actionableGaps` 把 `evidence_stale` 排在 `will_be_dropped` 之后、`approved_only` 之前
- **`preflightHeadline` 在 `analysis === 'approved'` 且 `requiredOpen` 含 `evidence_stale` 时**,文案要提「引用」或「重新分析」、且 `needsAnalysis` 为 true(对应「眼袋王」那种真实组合)

`apps/web/test/`(新建或就近追加)守住 `api.ts` 的运行时白名单 —— 它不触发 typecheck,必须有测试兜住:

```ts
// PREFLIGHT_TIERS 是硬编码的第二份档位清单,漏掉新档会让它被静默改判成
// will_be_dropped,新档一条都到不了界面。照 gap-source.test.ts 的源码断言写法。
```

## 不做

- **不改补充的默认目标**(见 §4)—— 会因保存强写「猜想」而制造本次要修的失效。要做需先让保存不降级目标文件,独立一项。
- 不改后端默认目标解析(`:203`)。
- 不给 `classifyGap` 加「资料是否被删」的探测 —— 要求失效引用作证已经把过时判定挡在门外,再探测是另一件事。
- 不动 `gapStats`(`enrich-types.ts`)那个「有答案 + `sourceStatus` 为 undefined 算 supplied」的兜底档。它是既有不一致,与本次分档是两套统计,合并需要单独评估。
- 不修 `intelligence-enrich.service.ts:284` 的强写降级本身,也不修 merge 输出无缩水守卫 —— 两条都在上一轮 PR 里记过,各自独立。
