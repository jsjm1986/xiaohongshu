# Agent 创作:素人代发种草模式

## 问题

Agent 创作通道产出的内容像品牌客服稿,和用户实际在发的素人种草帖差距很大。用 67 篇真实对标语料(`../70篇对标内容_AI提炼版.jsonl`,去重后 67 条)量过,差距有四处,其中一处是结构性的。

### 根因:校验强制机构答疑

`validation.ts:232-233` 要求每套候选的评论区必须混排「至少 2 条机构答疑」,而每条机构答疑又被 `:244-249` 强制要求带 `clarification` + `nextStep` + `boundary` + `stopReason` 四个字段。

这不是模型跑偏,是校验逼出来的。实测生成结果:

> 我们技术主打精准控量和内收紧,复发和凹陷几率很低,但凡事没有绝对,最终得医生面诊评估。

而真实语料里博主回复 187 行,**带机构口吻的只有 1 行(0%)**。真实的样子是:

```
评:是哪个白白哦?
博主回:老朱,朱冠锋呀
```

现实 0%,系统强制 ≥2 条。

### 另外三处

**免责声明混进交付字段。** `Cref.disclaimer` 是交付结构的一部分(`types.ts:141`),所以「以下为多角色评论情景演练与发布者答疑参考模板,不代表真实用户发言」这句话会直接出现在用户要粘贴到小红书的评论区里。它的读者是操盘手,不是平台用户。

**第一人称被禁。** `validation.ts:6` 的 `EXPERIENCE_CLAIM` 是 ERROR,而用户的核心打法就是素人第一人称。按校验的真实作用范围(`visibleCandidateText` 含正文**与**评论区)测那 67 篇:**命中 13 篇、19%**。

> 注:早前只扫正文得出「5 篇 7%」,那个数字低估了作用范围,已订正。

**标签带品牌词、正文把卖点说完。** 67 篇无一篇标签含品牌名,全是 `#成都眼袋#` 这类品类词加话题词。真实打法是正文只写处境和一个窄问题,参数(价格、恢复期、麻醉方式)留给评论区由博主回答。

## 设计

### 1. 模式开关

`agent-harness-core` 新增:

```ts
/** 素人代发种草模式。默认 peer_seeding。 */
export type HarnessSeedingMode = 'peer_seeding' | 'brand_voice';
export const DEFAULT_HARNESS_SEEDING_MODE: HarnessSeedingMode = 'peer_seeding';
```

`brand_voice` 保留现有全部严格行为,一个字节不差。

传递沿用 `bodyLength` 已经走通的那条通道:`validateHarnessCandidates` 的 `constraints` 加 `seedingMode?: HarnessSeedingMode`,缺省当 `peer_seeding`。

**两个调用点都必须传**:`runner.ts:848` 与 `agent-harness.service.ts:885`。漏一个,界面显示的校验结果与生成时的判定会分叉,这种 bug 极难查。测试要同时钉住两处。

不做成 `allowPeerSeeding: boolean`:`brand_voice` 是有实际用途的状态(通道里有 `brand` 发布身份、有「搜索决策补全」这类偏机构口吻的写法),两种模式的命名能说清这不是「关掉安全检查」,而是「换一种内容形态」。

### 2. 评论区结构

`validation.ts:232` 的拓扑要求按模式分叉:

| | brand_voice(现状) | peer_seeding(新) |
|---|---|---|
| 机构答疑 | ≥2 | 0 条也合格 |
| 博主回复 | 不计入 | **≥2** |
| 读者接话 | ≥1 | ≥1 |
| 短反应 | ≥1 | ≥1 |
| 线程总数 | 4—6 | 4—6 |

「博主回复」**不新增线程类型**,复用 `org_answer` 但要求 `postingIdentity === 'author'`。理由:这类线程的结构(有人问、有人答、可带追问)与机构答疑完全一致,差别只在谁在答;而 `author` 这个身份 `types.ts:80` 已经有了,不动类型定义。

四个强制字段按身份放宽:`peer_seeding` 下 `postingIdentity === 'author'` 的 `org_answer` 线程,`clarification` / `nextStep` / `boundary` / `stopReason` 改为可选。这四样正是把回复写成客服话术的直接原因。

`brand` / `staff` / `expert` / `publisher` 身份的线程**仍然全部要求**这四样,两种模式一致。机构一开口就得带边界和下一步,这是原设计里对的部分。

新增一条 ERROR:`peer_seeding` 下 `org_answer` 线程若 `postingIdentity !== 'author'` 且缺那四个字段,照旧报错——防止用「素人模式」当借口写机构口吻却省掉边界。

**JSON schema 也必须跟着改(自审补入)。** `runner.ts:71` 的 `THREAD_SCHEMA.required` 里含 `clarification`、`nextStep`、`stopReason`、`boundary` —— schema 层面就是必填。只放宽 `validation.ts` 不够:模型仍会被 schema 逼着为每条博主回复编出「可核验的下一步」和「停止原因」,客服味就是这么来的。

改法:把这四个键从 `required` 移出(仍保留在 `properties` 里,允许输出)。这是**两种模式共用的一份 schema**,所以 `brand_voice` 下的强制性由 `validation.ts` 继续保证 —— 那边四个字段缺失照旧 ERROR,行为不变。schema 只负责「允许不填」,校验负责「该填时必须填」。

同理 `stopReason` 的 enum 保留不动:博主回复不填它,填了也必须是那四个合法值。

### 3. 免责声明移出交付

`Cref.disclaimer` 从交付结构删除,连带五处:

```
types.ts:141        字段本身
runner.ts:127-129   JSON schema 的 required 与属性
runner.ts:289       长度上限表那一行
runner.ts:380       组装 Cref 时的读取
validation.ts:157   comment_disclaimer ERROR
validation.ts:37    simulationBlocked 清单里的这个码
```

模型从此不生成这句话。取而代之,`AgentHarnessPage.tsx:307` 那个位置放一条**固定提示条**,文案写死在前端:

> 这些是模拟问答参考,用来安排评论区节奏,不是已经发生的真实互动。

理由:这句话的读者是操盘手,不是平台用户。它属于操盘标注,不该由模型每次重新生成、更不该混进要粘贴出去的内容。写死在前端还能保证它不会因为模型这次漏掉而消失。

harness 自己的导出(`agent-harness.service.ts:1233`)保留这句提示,但改成常量而非读字段——导出的 Markdown 是给团队看的工作稿,标注该在。

`validation.ts:45` 的 `simulation_disclosure` 检查项判据里含 `comment_disclaimer`,删码后改成只看评论结构完整性与首评归属。

### 4. 第一人称拆两支

`EXPERIENCE_CLAIM` 一条正则现在管所有情况,拆成两条:

```ts
/*
 * 始终禁:营销化的口碑话术。两种模式都是 ERROR。
 * 67 篇真实语料命中 0 篇——这类词是伪造口碑的典型说法,不是真人的自然表达。
 */
const FABRICATED_TESTIMONIAL = /(亲测|我做过|我用过|我体验过|朋友做过|闺蜜做过|真实顾客|真实客户)/u;

/*
 * peer_seeding 放开,brand_voice 仍 ERROR。
 * 67 篇真实语料命中 13 篇——朴素的时间叙述(我做完两天了),不是营销话术。
 * 放开的理由:内容由真人素人账号发布、经历真实,AI 只是代笔起草。
 * brand_voice 保持 ERROR,因为机构不能假装自己是顾客。
 */
const FIRST_PERSON_TIMELINE = /(?:我|朋友|闺蜜|同事|姐妹|家人).{0,12}(?:刚做|做完|做了|做的|术后|恢复)/u;
```

`fabricated_experience` 这个错误码不在任何 `*_ERROR_CODES` 分组里,所以它只通过「任何 error 都阻断终稿校对」那条生效。拆分不影响分组,无需改 `publicationChecklistFor`。

### 5. 标签禁品牌词

`peer_seeding` 下新增 WARNING(不是 ERROR):标签含项目名或产品名时提示。判据是拿本轮证据里的项目名/产品名比对,不维护关键词表。

用 WARNING 的理由:品牌词判定靠字符串匹配项目名,容易误伤(项目名可能含通用词)。67 篇无一篇带品牌名,但那是人的判断力,硬规则替代不了。给提示、不阻断导出。

### 6. 正文留白:只进提示词,不做校验

「正文不许把卖点说完」本质是留白手感,写成规则要么太松没用、要么太严逼模型删掉必要信息。改成写进 `peer_seeding` 的提示词。

## 提示词

`runner.ts` 里 `peer_seeding` 追加素人代发指引,`brand_voice` 保持原样:

- 正文由真人账号第一人称写,可以写自己的时间线(刚做完、第几天),不写成科普或参数罗列
- 具体参数(价格、恢复期、麻醉方式、能否当天做)优先留给评论区由博主回答
- 评论区至少两条由博主本人(`author`)回复,口气是朋友聊天不是客服答疑
- 医生/人物名字优先由提问者带出来、博主确认,正文不必写全名
- 标签用品类词和城市词,不堆品牌名

**必须改写一句现有提示词,否则模式自相矛盾。** `runner.ts` 的线程指引里有:

> Never invent treatment, visit, friend/colleague case, recovery day, outcome, purchase, endorsement or observed demand in any simulated reader voice.

这句禁止的正是 `peer_seeding` 要的东西——博主回复「两个月了」「我刚做完」就是 recovery day 与 outcome。`peer_seeding` 下要把它改成:发布账号(`author`)可以叙述自己的真实时间线与结果;**模拟读者**(`reader_exchange` / `organic_reaction` 的虚构昵称)仍然不得被编造经历、朋友案例或购买行为。

这条区分是本设计的要害:放开的是**真人发布账号的自述**,不是**虚构读者的证言**。前者由真人负责,后者无人负责。

`methods.ts` 各写法的 `boundaryPolicy` 里「不得编造第一人称体验」这类措辞需按模式区分表述,不能与放开后的行为自相矛盾。

## 测试

9. 标签含项目名 → WARNING 且不阻断导出
