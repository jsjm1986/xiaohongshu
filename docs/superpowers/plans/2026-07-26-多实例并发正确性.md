# 多实例并发正确性

## 问题

DB 引擎层已经是安全的:`database.service.ts:37` 开了 `journal_mode = WAL`、
`busy_timeout = 5000`、`foreign_keys = ON`,`transaction()` 用 `BEGIN IMMEDIATE`
前置获取写锁并用 savepoint 支持嵌套。多用户并发读写不丢数据、不崩。

缺陷全部在**进程内状态假设了「本进程独占这个 DB」**。四处:

**1. 生成任务恢复误杀他人**(`generation-restart-recovery.ts:50-81`)
`recoverInterruptedJobs` 无条件抓**全表** `queued`/`running` 重置。B 实例启动会把
A 实例正在跑的 job 判成「被重启打断」,`restartInterruptions` +1 并标回 `queued`
重新入队。后果:同一 job 被两实例并发执行(重复烧模型调用),三轮误判后触顶判
`failed`。

实测已发生:job `02926b8c` 与 `b8ac09ac` 报「任务被应用重启多次打断(3 次)」,
而实际上没有任何一次真正的重启 —— 是两个 API 进程共用 `data/app.db` 互相误判。

**2. 分析任务恢复更激进**(`intelligence.service.ts:186-192`)
无条件把全表 `queued`/`running` 的 `analysis_tasks` 直接标 `failed`。B 实例启动
即杀掉 A 正在跑的分析。分析任务是 insert 时直接 `'running'` 的 inline 执行
(`intelligence.service.ts:1798-1802`),没有队列,所以它只需要归属过滤,不需要领取。

**3. 队列是进程内内存**(`generation.service.ts:216-218`)
`queue: string[]` / `activeJobs` / `maxConcurrentJobs = 2`。三个后果:
- `maxConcurrentJobs` 是**每实例**上限,3 实例就是 6 路并发打同一个 BYOK 密钥,
  加剧凭据池冷却(实测中继持续返回「全池冷却,返回 429 + Retry-After」近一小时);
- `queuePosition`/`queueLength` 只反映本实例,用户看到的排队位次在多实例下是错的;
- `failQueuedForOutage`(`:693`)只遍历本实例内存队列,别的实例上同项目的排队任务
  不会被清 —— 而这个函数存在的全部意义就是避免每篇再花 16 分钟撞同一面墙。

**4. 配额超发**(`settings.service.ts:140-146`)
`consumePlatformQuota` 是 check-then-write:`SELECT` 读 `quota_used` → JS 比较 →
`UPDATE ... + 1`,且调用点(`generation.service.ts:296`)在事务**外**。

注意:这条**只在多实例下发生**。函数全程同步(`row()`/`ensure()` 都是同步
SQLite),单实例 Node 事件循环内不会被抢占。

## 方案

DB 成为唯一权威。目标是多实例下正确(不重复执行、不误杀、不超发),同时单实例
下行为不变且更稳。SQLite 仍是单文件,不追求水平扩容吞吐。

### 迁移 14

`generation_jobs` 加三列 + 一个索引:

```sql
ALTER TABLE generation_jobs ADD COLUMN claimed_by TEXT;
ALTER TABLE generation_jobs ADD COLUMN claimed_at TEXT;
ALTER TABLE generation_jobs ADD COLUMN heartbeat_at TEXT;
CREATE INDEX generation_jobs_claim_idx
  ON generation_jobs(status, claimed_by, heartbeat_at);
```

`analysis_tasks` 加两列(无队列,只需归属 + 心跳):

```sql
ALTER TABLE analysis_tasks ADD COLUMN claimed_by TEXT;
ALTER TABLE analysis_tasks ADD COLUMN heartbeat_at TEXT;
```

`SCHEMA_VERSION` 13 → 14(常量改一处,`database.service.ts:16`)。

存量行 `claimed_by` 为 NULL —— 恢复逻辑要把「NULL 且 running」当作**上一代进程
留下的孤儿**接管,否则升级那一刻的在跑任务会永久卡住。

### 实例身份

`ApiOptions` 加 `instanceId: string`,默认 `${hostname()}:${pid}:${randomUUID().slice(0,8)}`,
可用 `CONTENT_AGENT_INSTANCE_ID` 覆盖(容器编排下可注入稳定 id)。

心跳间隔与超时进 config:`CONTENT_AGENT_JOB_HEARTBEAT_MS`(默认 15_000)、
`CONTENT_AGENT_JOB_CLAIM_TIMEOUT_MS`(默认 90_000)。超时必须显著大于心跳间隔 ——
取 6 倍,容忍单次长事务或 GC 停顿造成的心跳延迟,不会把健康实例的任务判死。

### 原子领取

新模块 `apps/api/src/job-claim.ts`,纯函数 + `DatabaseService`,不依赖 Nest。

```
claimNextJob(db, instanceId, now): string | undefined
  UPDATE generation_jobs SET status='running', claimed_by=?, claimed_at=?, heartbeat_at=?, updated_at=?
  WHERE id = (
    SELECT id FROM generation_jobs
    WHERE status='queued' AND deleted_at IS NULL
    ORDER BY created_at, id LIMIT 1
  ) AND status='queued'
  → changes === 1 才算领到;否则说明被别的实例抢先,返回 undefined
```

`AND status='queued'` 是必需的守卫:子查询与 UPDATE 之间存在竞态窗口,靠 WHERE
再确认一次让领取真正原子。SQLite 的单写者模型保证同一时刻只有一个 UPDATE 生效,
所以两个实例不可能都拿到 `changes === 1`。

领取即置 `running`(不再由 `process()` 置),这样「被领取」和「在跑」是同一个原子
事实,不存在中间态。

### 心跳与回收

`heartbeatJob(db, jobId, instanceId, now)`:
```
UPDATE generation_jobs SET heartbeat_at=?, updated_at=? WHERE id=? AND claimed_by=?
```
`changes === 0` 说明本实例已丢失所有权(被回收过),`process()` 应中止后续写入 ——
避免两个实例同时写同一个 job 的产出。

`reclaimStaleJobs(db, instanceId, now, timeoutMs)` 替换 `recoverInterruptedJobs`:

| 行内状态 | 处理 |
|---|---|
| `queued`,任何 `claimed_by` | 不动。它本来就在等领取,谁都能领 |
| `running`,`claimed_by` = 本实例 | 本实例重启前留下的。归还 `queued`,`restartInterruptions` +1 |
| `running`,`claimed_by` = 别的实例且心跳新鲜 | **不动**。别人在正常跑 —— 这是修掉误杀的关键 |
| `running`,`claimed_by` = 别的实例但心跳超时 | 该实例已死。归还 `queued`,+1 |
| `running`,`claimed_by` IS NULL | 迁移前的存量孤儿。归还 `queued`,+1 |

`RESTART_INTERRUPTION_LIMIT = 3` 语义保留:超限判 `failed`。但现在计数只在**真实**
中断时累加,不再被其它实例的启动污染。

后台定时器每 `heartbeatMs` 跑一次 `reclaimStaleJobs` —— 不只在启动时跑,否则一个
实例中途崩掉,它的任务要等到下次有实例启动才被回收。

### 队列改为 DB 驱动

`queue: string[]` 与 `activeJobs` 删除。`drainQueue()` 改为:

```
while (this.activeJobs < maxConcurrentJobs) {
  const jobId = claimNextJob(db, instanceId, nowIso());
  if (!jobId) break;              // 没有可领的了
  this.activeJobs += 1;           // 仍需本地计数:它约束的是本实例并发度
  setImmediate(() => process(jobId).finally(() => { activeJobs -= 1; drainQueue(); }));
}
```

`activeJobs` 保留为本地计数是对的 —— 它约束的是**本实例**的并发度(内存、
本地 CPU),不是全局资源。全局模型并发另有 `modelMaxConcurrentRequests` 管。

`enqueue(jobId)` 不再 push,只 `drainQueue()`:job 已在 DB 里是 `queued`,DB 就是队列。

`queuePosition(jobId)` 从 DB 算:
```sql
SELECT COUNT(*) + 1 AS position FROM generation_jobs
WHERE status='queued' AND deleted_at IS NULL
  AND (created_at, id) < (SELECT created_at, id FROM generation_jobs WHERE id=?)
```
`queueLength()` 同样 `COUNT(*) WHERE status='queued'`。两者现在是全局真值,多实例下
用户看到的位次正确。

`failQueuedForOutage(projectId, reason)` 改为直接 UPDATE,覆盖所有实例的排队任务:
```sql
UPDATE generation_jobs SET status='failed', error=?, progress=100, completed_at=?, updated_at=?
WHERE project_id=? AND status='queued' AND deleted_at IS NULL
```
`changes` 即清掉的条数。「只清同项目」的多租户约束保留(注释里写明的理由不变)。
需要先 SELECT 出被清的 id 以便逐条写 `event`。

### 配额原子化

`consumePlatformQuota` 把检查下推进 SQL:

```sql
UPDATE workspace_settings SET quota_used = quota_used + 1, updated_at = ?
WHERE workspace_id = ? AND quota_used < monthly_quota
```
`changes === 0` → 抛 `ForbiddenException(QUOTA_EXHAUSTED_MESSAGE)`。

单条语句既检查又自增,并发下不可能超发。`refundPlatformQuota` 已经用
`MAX(0, quota_used - 1)`,本身是原子的,不动。

### 分析任务

`intelligence.service.ts:186` 的 `onModuleInit` 改为只标记「确实属于本实例或心跳
超时」的任务:

```sql
UPDATE analysis_tasks SET status='failed', error=?, completed_at=?, updated_at=?
WHERE status IN ('queued','running') AND deleted_at IS NULL
  AND (claimed_by = ? OR claimed_by IS NULL OR heartbeat_at < ?)
```

插入时写 `claimed_by = instanceId` + `heartbeat_at`(`:1798-1802`),执行期间续心跳。
分析任务的语义仍是「重启即失败、重试安全」—— 不改成重跑,因为它是同步 inline 的,
没有队列可回。改的只是**不再杀别人的**。

## 落地顺序

1. 迁移 14 + `SCHEMA_VERSION` + `instanceId`/心跳超时进 config
2. `job-claim.ts`:`claimNextJob` / `heartbeatJob` / `reclaimStaleJobs`,配套单元测试
   (两实例竞争同一 job、心跳新鲜不回收、心跳超时回收、NULL 孤儿接管、超限判 failed)
3. `generation.service.ts` 接线:`drainQueue` 走 claim、`queuePosition`/`queueLength`
   走 DB、`failQueuedForOutage` 走 UPDATE、心跳定时器 + 回收定时器、`process()` 在
   心跳失效时中止
4. 配额原子化 + 并发超发测试
5. 分析任务归属过滤 + 测试
6. 删除 `generation-restart-recovery.ts`,其测试改指 `reclaimStaleJobs`

## 验证

- `generation-queue-position.test.ts` 现在直接往 `service.queue` 里 push
  (`:86`),队列改 DB 后这个注入方式失效 —— 改为 seed `status='queued'` 的行,
  按 `created_at` 排序断言位次。这是测试**变得更真**,不是放宽。
- 新增多实例并发测试:同一 `dataDir` 起两个 `DatabaseService`,验证
  (a) 同一 job 只被一个实例领到;(b) A 在跑时 B 启动不改 A 的 job;
  (c) A 心跳停止后 B 能回收;(d) 并发 `consumePlatformQuota` 到上限不超发。
- `provider-outage-queue.test.ts` 的 6 个用例语义不变,但内部从内存队列改为 DB,
  断言应保持通过(跨项目不牵连、空队列返回 0 等)。
- 三套全量:agent-core / apps/api / apps/web。apps/web 有 1 个既有失败
  (`comment_multi_turn_growth` 快照),与本次无关。

## 不做

- 不引入外部队列(Redis/BullMQ)。SQLite 单文件 + claim 足够支撑目标形态,
  加中间件是另一个量级的运维成本。
- 不做全局并发上限。`maxConcurrentJobs` 保持每实例语义;真正需要全局约束的是
  模型并发,那由 `modelMaxConcurrentRequests` 和中继侧的凭据池负责。
- 不改 `refundPlatformQuota`,它已经是原子的。
