# 极简创作:四区标签改为真频道路由

## 为什么现在改

四个区(总览 / 知识库 / 创作 / 产出)现在是 `useState<QuickTab>` 切渲染,地址栏全程 `/quick`。这不是"还没来得及做路由",而是**已经在手写一个路由器**:

- 上一轮为了让阅读页能返回原处,往 sessionStorage 塞了 `{projectId, tab}`(`lib/quick-nav.ts`),并在 `QuickChannelPage` 里加了一个恢复 effect + 一个记忆 effect + 主动清记忆——这三段就是路由的替代品
- 刷新页面掉回项目卡墙;分享链接只能分享到"极简创作首页";浏览器后退直接跳出整个工作区
- 阅读页(`/quick/read/:jobId`)已经是真路由,同一个壳里两套导航模型

已确认的两个决定:

1. **地址形状**:`/quick/:projectId/:area` —— 项目进地址,刷新与分享都能精确回到同一项目的同一区
2. **在途状态保留**:跨区走动时创作区的勾选/预设/结果不丢,行为与现在的 tab 一致

## 一、路由

```
/quick                                  项目卡墙(QuickHome)
/quick/:projectId                       → 重定向到 /quick/:projectId/overview
/quick/:projectId/overview              总览
/quick/:projectId/knowledge             知识库
/quick/:projectId/create                创作
/quick/:projectId/history               产出
/quick/read/:jobId                       阅读页(不动)
/quick/account                          账户页(不动)
```

`:projectId` 与固定段 `read` / `account` 会冲突(都能匹配 `/quick/:x`)。React Router 的 rank 规则里静态段优于动态段,所以 `read`/`account` 会正确胜出;但这依赖顺序直觉,要加测试锁死。

`area` 用白名单解析:不认识的值(手改地址、旧链接)一律按 `overview` 处理并 `replace` 掉地址,不留一个渲染空白的路由。

## 二、状态归属:新增 QuickWorkspaceProvider

现在 19 个 `useState` 全在 `QuickChannelPage` 里。改路由后该组件按区卸载,跨区共享的那批必须上移。

**提到 provider**(活过路由切换):

| 状态 | 为什么 |
|---|---|
| `opportunities` / `opportunityId` | 知识库分析完灌给创作区;选中项决定右栏 |
| `presets` / `presetId` / `overrides` / `imageAssetIds` | 创作区在途配置 |
| `checkedIds` / `batchMode` / `batchPresetIds` | 批量勾选——"去产出区确认一下再回来"是常见动作 |
| `results` / `jobId` | 刚生成还没处理的结果 |
| `history` | 产出列表,总览页也读它算摘要 |
| `activeBatchId` / `focusJobId` | 跨区交接的落点标记 |

**留在页面局部**(本来就不该跨区活):`busy`、`generating`、`loadingHistory`、`statusFilter`、`keyword`、`expanded`。

`project` 不进 provider 的 state:它由 `:projectId` 派生(在 `projects` 里查),这是路由化的核心收益——单一真源。

provider 挂在 `/quick/:projectId` 这一层的布局路由上,`key={projectId}`:换项目时整体重挂,天然完成现在 `onProjectChosen` 里那 12 行手工清理。`clearDownstreamOfProject()` 因此可以删掉。

## 三、导航

`goTo(tab)` → `navigate(areaPath(projectId, area))`。签名从 `(tab: QuickTab) => void` 变成同形状的函数,`OverviewTab` / `CreateTab` / `ProjectKnowledgeTab` 的 props 不用改——它们只调用,不关心实现。

步骤条从 `<button onClick>` 改成 `<NavLink>`:可中键新开、可右键复制链接,`aria-current` 由 router 给。

`fail()` 里 `GenerationStillRunningError` 那条兜底路径(`setActiveTab('history')` + `setFocusJobId`)改成 `navigate` 带 state 传 `focusJobId`。

## 四、可以删掉的东西

- `lib/quick-nav.ts` 的 `rememberWorkspace` / `recallWorkspace` / `forgetWorkspace` / `parseWorkspaceMemo` / `serializeWorkspaceMemo` 与 `QuickWorkspaceMemo`:地址本身就是记忆。`readerPath` 保留
- `QuickChannelPage` 的恢复 effect、记忆 effect、`clearWorkspace` 里的清记忆
- `lib/quick-channel-state.ts` 的 `clearDownstreamOfProject` / `clearResults`(改由 provider 重挂承担)
- `test/quick-nav.test.ts` 里 memo 相关的 6 项(readerPath 的 2 项保留)

阅读页的「返回产出」改为 `navigate(areaPath(job.projectId, 'history'))`,不再写 sessionStorage。

## 六、验证

单测(`quick-routes.test.ts`):
- `areaPath` 四个区 + projectId 转义
- `parseArea` 白名单:四个合法值、未知值落 `overview`、空值落 `overview`
- 静态段优先:`/quick/read` 与 `/quick/account` 不被 `:projectId` 吃掉(用 router 的 `matchRoutes` 断言,不靠直觉)

浏览器实测(逐条对比改前行为):
- 四个区点一圈,地址随之变化;每个区刷新后停在原处,不掉回卡墙
- 浏览器后退/前进在四区之间走,不跳出工作区
- 在创作区勾 3 个选题 → 去产出区 → 后退回创作区,勾选仍在(这是"保留"决定的验收点)
- 换项目后勾选与配置被清空(provider `key` 重挂)
- 阅读页「返回产出」落在同一项目的产出区
- `/quick/不存在的id/overview` 与 `/quick/:id/不存在的区` 的落点
- SaaS 探针用户:四个区地址全部可达,专家版路径仍 403/弹回

后端不动:`isSaasApiAllowed` 白名单是按 API 路径判的,前端路由形状与它无关。

## 七、不做

- 不动四个区的信息结构与内容(这轮只改导航模型)
- 不加"区级权限门控":四区常开是既定设计
- 不动专家版
