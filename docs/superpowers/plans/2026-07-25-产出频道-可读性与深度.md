# 产出频道:可读性与深度重做

## 现状实测

`GET /api/generations/:id` 每个候选返回 37 个字段,「查看」只渲染 11 个。缺的不是零碎字段,而是**「为什么是这篇、这篇能不能发」那一整层**。

按 168 个真实内容包统计,已经算好、存在库里、但界面一个字都没露出的:

| 数据 | 覆盖 | 现状 |
|---|---|---|
| `reasoning` 句子级事实/假设标注(8–35 条/篇) | 168/168 | API 根本不返回 |
| `gapCoverageLedger` 缺口落地台账 | 168/168(**204 条里 168 条 `realization_failed`**) | 不返回 |
| `gapPlanningCards` 缺口原始问题与边界 | 168/168 | 不返回 |
| `strategy` 候选表达轴(原型/正文角色/叙述/声音) | 168/168 | 不返回;三个候选都叫「随机候选」 |
| 评论线程身份与角色(834 条) | 834/834 | 丢掉 `postingIdentity`/`personaRole`/`function`/`gap` |
| `sources` 证据出处 | 51/168 | 不显示 |

另外两个确定的缺陷:

1. **结论行 85% 报错了重点。** 129 个未通过候选里,110 个(85%)`firstValidationIssueLabel` 取到的首条是 `warning`。截图就是这样:8 个 error 里挑出一条 warning「正文长度偏离样本形态目标」当结论,真正的「敏感宣称缺证据」被折叠进「另有 9 项」。用户按显示的那条去改,改完还是不能导出。
2. **一次「查看」下载 1.05 MB。** 3 候选 × 234 KB,其中 `trace`(61 KB)+`parameterImpactReport`(53 KB)+`orchestrationSnapshot`(25 KB)占 90%,极简创作一个都不渲染。

「查看」里只有复制和导出,没有修改、没有重试——失败任务只能去批次看板重试,列表里的失败条目没有入口。

## 一、后端:只读阅读投影接口

`apps/api/src/generation-reader-view.ts`(新,纯函数,不依赖 Nest)

`readerView(pkg: ContentPackage)` → 只含阅读与决策要用的字段:

- 成品:`title` / `body` / `tags` / `imageBrief` / `disclaimer` / `ownedFirstComment`
- 评论:每条带 `question`/`answer`/`function`/`postingIdentity`/`personaRole`/`stage`/`gap`/`boundary`/`nextStep`/`simulated`/`displayName`/`followUps`
- 判断依据:`reasoning`(只留 `statement`/`status`/`location`/`occurrence`/`evidenceIds`,丢 `sourceSpans` 里的大段原文)、`gapLedger`、`gapCards`、`sources`、`unknowns`
- 候选差异:`strategy` 的 7 个轴 + `seed`
- 结论:`validation`(原样,前端自己分级)、`deploymentPlan`

明确**不含** `trace` / `parameterImpactReport` / `orchestrationSnapshot` 全量 / `resolutionSnapshot` / `configSnapshot` / `knowledgeSnapshot`。

实测投影后每任务 **中位 36 KB、最大 68 KB**(现 1.05 MB)。

- `generation.service.ts`:加 `readerView(jobId)`,走 `packageRows` + 上述纯函数。
- `generation.controller.ts`:`@Get(':id/reader')`,`project.read` 权限,与 `:id` 同一套 assert。
- `saas-access.ts` 不用改(`inScope('/api/generations')` 已覆盖子路径),但要加测试**证明**它放行。
- 完整版工作台继续用 `GET /api/generations/:id`,不动。

测试 `apps/api/test/generation-reader-view.test.ts`:字段集逐项锁死(白名单相等,不是「包含」)、重字段确认缺席、`reasoning`/`gapLedger` 真的有值、SaaS 会话能取到、跨项目 403。

## 二、结论分级(修 85% 错重点)

`apps/web/src/lib/issue-verdict.ts`(新)

`issueVerdict(validation)` 返回:

```
{ publishable, blocking: [{label, code, count}], advisory: [...], headline }
```

- error 与 warning **分开**,error 永远排前,同级按出现次数降序。
- headline 用首个 **error**;没有 error 只有 warning 时说明「可发布,但有 N 项建议人工核对」。
- 未识别 code 保留英文原文(沿用 `validation-labels.ts` 的既有原则)。

替换 `QuickResult.tsx` 与 `HistoryTab.tsx` 两处各写一遍的结论块为 `ValidationVerdict.tsx`,文案分两段:**「须处理才能导出」** 与 **「可人工核对后使用」**。

测试:用真实截图那个候选的 code 序列(w,w,e,e,e,e,w,e,e,e,w,e)锁死 headline 必须是 error 那条。

## 三、深度三块

### 3.1 缺口落地台账 `GapCoverageCard.tsx` + `lib/gap-ledger.ts`

每个选中缺口一行:原始问题(来自 `gapCards`)→ 计划由哪些通道回答 → 实际落地情况。`realization_failed` 时列出缺哪几项(`answer` / `condition_or_boundary` / `evidence` / `findability`),用中文说明,并点明这正是「不能直接发」的原因。状态映射覆盖实测出现的 4 种(`realization_failed` / `unknown_with_verification` / `body_resolved` / `thread_resolved`),未知状态原样显示。

### 3.2 事实标注 `FactLedgerCard.tsx` + `lib/fact-ledger.ts`

`reasoning` 按 `occurrence.field` 归到通道,给出「正文 5 句:0 句有证据 / 5 句为假设」这类计数,并列出每条陈述及其状态与证据编号。

实测可行性已验:`occurrence.field==='body'` 的 498 条**全部**是正文的精确子串(100%),线程级 2371 条中 2252 条(95%)能匹配到对应线程文本——所以可以做到点一条陈述高亮它在正文里的位置;匹配不到的一律只列文字不高亮,不猜。

### 3.3 候选差异 `CandidateDiffBar.tsx` + `lib/candidate-diff.ts`

把三个「随机候选」换成可区分的标签。**重要约束**:只有 `prototype` 是封闭枚举(8 个值,可做中文映射);`bodyRole`/`narrativeMode`/`voice`/`commentMode`/`openingMode` 实测是开放词表(几十种,含模型产出的中文自由文本),**必须原样显示,不做映射、不猜译**。

只显示候选之间**真正不同**的轴(全同的轴不占版面),并保留 `seed`。

## 四、动作补齐

- **按意见修改**:产出区接上 `reviseCandidate`(后端 `POST :id/revise` 已存在且对 SaaS 放行,创作区已在用)。要明说消耗 1 次额度(`generation.service.ts:498` 确实会 `consumePlatformQuota`)。
- **单篇重试**:把 `BatchBoard.retry` 里那段(选题+预设→`resolveRecipeTargets`→审批→单任务批次)抽成 `lib/single-retry.ts`,批次看板与产出区列表共用,失败条目直接可重试。同样标注额度。
- **逐段复制 + 按发布顺序复制**:标题/正文/标签/评论各自的复制已有;补一个「按发布顺序复制」(正文+标签一份,评论区一份),贴到小红书时不用手工拆。

## 五、评论区可读性

现在评论渲染成一列 Q/A,看不出谁在说。用 reader 接口新增的字段补上:模拟读者 vs 可追责账号(`postingIdentity`,实测 author/publisher/staff/expert 四种)、承担的缺口、线程功能(clarify/verification/counterexample/surface_gap/next_step/answer 六种)。追问只有 42/834 条有,有才显示。

`postingIdentity`/`function` 是封闭枚举,做中文映射;`personaRole`/`voice` 是开放文本,原样显示。

## 六、版面

产出区详情面板从 `max-width: 1120px` 放宽,并把「成品 / 判断依据 / 发布方案」分成三段而不是一条长流。新增卡片沿用既有 `--v2-*` token,不引入新变量。

## 验证

- 两包 `tsc --noEmit` + 全量测试。api 基线是 main 上就红的 4 个失败(`viewer can read but cannot write projects`、`read-only API keys are workspace-scoped`、`formula registry...`、`planning CRUD...`),只对比这个基线。
- 用真实浏览器(puppeteer + 系统 Chrome)打开截图里那个「统一转化行动」任务,确认:结论行报的是 error 而不是长度警告、缺口台账显示 `realization_failed` 的具体缺项、三个候选标签可区分、修改与重试按钮真的可点。
- 实测 reader 接口响应体积,确认落在 36 KB 量级。

## 不做

- **`revisions` 历史**:168 个包全部为空,做出来是空壳。
- **`parameterImpactReport` / 参数影响报告**:属于完整版工作台的专家视角,极简创作放进来只会加噪声。
- **删除/归档产出**:要加 `deleted_at` 迁移和 DELETE 端点,删除语义与撤销策略得先定,单独一轮。
