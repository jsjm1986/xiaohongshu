# 校验器误报治理

## 审查方法

三个维度交叉核对，不靠单例判断：

1. **实现层**：盘出全部词面比对辅助函数及其每个调用点对应的 issue code；
2. **数据层**：229 个落库候选包的 issue 频次、严重度分布、字段实测值；
3. **意图层**：对照测试名与断言，判断当前行为是否偏离原设计。

## 盘点：全部词面比对探测器

| 函数 | 位置 | 调用点 | 影响的 code |
|---|---|---|---|
| `semanticallyConnected` | `artifacts.ts:29` | 4 处 | `plan_to_copy_alignment` |
| `anyConnection` | `artifacts.ts:45` | 2 处 | 同上 |
| `explicitBoundaryContradiction` | `artifacts.ts:63` | 1 处 | 同上（`fail` 分支） |
| `realizesText` | `content.ts:881` | 6 处 | 缺口三兄弟 + `knowledge_backed_claim_unrecorded` |

`semanticallyConnected` 的判据是 bigram Dice 系数 ≥0.2 或字符重合率 ≥0.42；
`realizesText` 的判据是**逐字包含**（或每个分片都被包含）。两者都在做语义判断。

## 缺陷一：对齐检查的 4 个 warn 分支是纯噪声

**证据 A（严重度）**：202 次命中**全部是 warning，`fail` 一次未触发**。
真正有价值的矛盾检出（`explicitBoundaryContradiction`）从未误伤，噪声全部来自
4 个「没找到承接就提示复核」的 warn 分支。

**证据 B（比对双方的性质不对等）**：`imagePlan.frames` 去重后只有 **16 种**固定
模板短语（「保留普通生活背景」「让变化从场景里被看见」），而 `imageBrief` 229 条
**全不重复**且内容具体（「手机随手拍的眼下自拍，右眼下有一点点泛红，背景是办公桌
角落，自然光」）。抽象编排指令与具体画面描述之间不存在词面重叠，判 warn 是必然
结果，与文案质量无关。

**证据 C（禁止性边界的方向错误）**：边界条目 1835 次中 **59% 是禁止性表述**
（「不得贬低其他医疗项目」「不承诺零增项」「AI不能判断用户是否适合项目」）。
这类边界正确的落实方式就是**可见文案不出现该内容**，而
`boundary_continuity` 的 warn 分支要求「在可见文案中找到边界的可解释承接」——
遵守边界反而被判可疑。方向反了。

**证据 D（检查器自认判不准）**：4 个 warn 分支的措辞分别是「中文改写可能造成词面
差异」「不把词面不一致当作硬失败」「这可能是同义改写」「边界也可能作为隐式守则
生效」。实现者已经知道这个判据不可靠，用措辞免责，但仍然发了提醒。

**证据 E（零真实缺陷）**：报此 code 的 202 个包中，`imageBrief` 为空的有 **0 个**，
有内容的 202 个。唯一真正有价值的 warn 分支（「图片说明为空」）从未触发。

**设计意图佐证**：`artifacts.test.ts:177` 的测试名是
`fails only an explicit positive instruction that reverses a prohibitive boundary`
——「**只有**当文案出现与禁止性边界相反的明确正向指令时才失败」。当前的 4 个 warn
分支超出了这个意图。

## 缺陷二：缺口落地判定要求逐字包含，与极简创作直接冲突

`realizesText` 要求可见文案**逐字包含**计划答案。实测：

- 计划答案长度中位数 **43 字**（最长 100 字），书面语；
- 实际正文长度中位数 **67 字**（极简创作刻意压到 120 字内，且要求口语化）。

要求 67 字口语正文逐字包含 43 字书面语答案，结构性不可能。这不是模型没写好，
是两个要求互相冲突。

**实例对照**（抽自真实落库数据）：

- 计划答案：「普通AI客服是客户问一句答一句；美冠AI解决的是'这个客户是谁、现在处于
  什么阶段、下一步应该做什么'，包括客户记忆、业务判断、主动跟进、人工接管、知识
  管理和安全审计。」
- 实际正文：「朋友推荐美冠AI，说它能记住客户顾虑、主动跟进，关键时候转人工。」

核心信息（客户记忆／主动跟进／人工接管）全部落实，是恰当的口语化改写。但判定结果
是 `missing: answer, condition_or_boundary, evidence, findability` —— **四项全缺**。
四项同时全缺是比对没对上的特征，不是内容缺失的特征。

同一份 `card.boundary`（「不能贬低竞品，只客观对比」）也是禁止性的，
`conditionOrBoundaryRealized` 却要求正文包含它。

**叠加放大**：`resolved` 是 5 个条件的合取，任一不满足就同时触发三条 code
（`gap_resolution_not_realized` / `planned_body_gap_not_realized` /
`planned_comment_gap_not_realized`），一份缺陷被拆成三条提醒重复播报，观感噪声
放大三倍。

## 缺陷三：AI 判官的裁决不落库，形成观测盲区

**先更正一个此前的错误结论。** 我原先根据「229 个落库包 `claimJudgments` 全为 0」
判断判官被跳过或从未产出结果。**这个结论是错的。**

逐层排查后的事实：

1. 判官在 `engine.ts:2399` 被无条件调用（只要 `provider && useProvider`）；
2. 两个早退分支都不成立 —— `collectUnanchoredSensitiveClaims` 的判据
   （`genericMeasuredClaim` / `marketingPromiseClaim` / claim_policy terms）比校验层
   **更宽**，不会为空；`knowledgeAnchorEvidencePool` 实测恒 ≥1（`planningContext`
   总会提供一条 `kind:"fact" / user_supplied` 的引用，已实测验证 pool=1）；
3. 没有任何 `model_claim_judge_failed` 信号，说明调用也没失败；
4. **根因**：`claimJudgments` 只定义在 `GenerationDraft`（`types.ts:1989`）上，
   `ContentPackage` **没有这个字段**，组包时从未复制过去。

所以判官在校验时是**生效的**（`content.ts:1400` 的 `claimJudgmentByStatement`
会消费它，裁决为 `factual_assertion` 之外或 `supported === true` 时放行 error），
只是裁决结果不落库，事后无法审计。229 个包的 0 是观测盲区，不是判官缺席。

这也意味着：`sensitive_claim_without_evidence` 剩下的 67 例中，有多少是判官判过
`unsupported`（真无据）、有多少是判官没覆盖到，目前**无法区分**。必须先把裁决
落库才能回答。

## 不改的部分（交叉验证后确认是真实信号）

- `comment_network_length_drift` 36%、`comment_network_under_grown` 21%：命中率不
  虚高，此前人工读过内容确认有真实命中（一篇评论区确实过长被正确拦下）。
- `knowledge_backed_claim_unrecorded` 67%：与 `model_ledger_failed` 交叉分析显示
  92 例台账失败连带、**62 例台账成功仍报**。抽查后者其中一例：26 条 reasoning 只有
  1 条 `fact`，模型确实没登记事实。这是真问题，保留。
- `explicitBoundaryContradiction` 的 `fail` 分支：从未误伤，保留。
- `sensitive_claim_without_evidence` 29%：此前已确认其 fallback 是刻意设计
  （13 条测试断言「判官缺席→error 保留」），不动。

## 修复方案

### 1. 对齐检查：warn 分支只在「确实缺失」时提醒

`artifacts.ts` 的 4 个 warn 分支改为：

- `image_plan_to_brief`：保留「imageBrief 为空 → warn」；把「有内容但词面不匹配」
  从 `warn` 降为 `not_evaluated`，理由写明词面判据无法判定同义改写。
- `cover_promise_to_copy` / `planned_anchor_to_copy`：同上，词面不匹配 →
  `not_evaluated`。
- `boundary_continuity`：**禁止性边界不参与承接检查**（新增
  `isProhibitiveBoundary()` 判别），只保留 `explicitBoundaryContradiction` 的
  `fail` 检出；非禁止性边界的词面不匹配 → `not_evaluated`。

`not_evaluated` 不进 issue 列表，所以 `plan_to_copy_alignment` 只在真有矛盾
（`fail`）或图片说明为空时出现。

### 2. 缺口落地：区分「未落地」与「无法用词面判定」

`content.ts`：

- `conditionOrBoundaryRealized`：禁止性 `boundary` 不要求正文包含（复用同一个
  `isProhibitiveBoundary()`），改为「未发现反向表述即通过」。
- 新增 `realizationConfidence`：当 `answerRealized` 为 false 但
  `findable`（线程存在且有答复）为 true 时，标记为 `unverifiable_by_lexical_match`
  而非 `missing`。
- 三条 code 合并播报：同一 gap 同一轮只发一条
  `gap_resolution_not_realized`，message 里列明通道与缺失项；
  `planned_body_gap_not_realized` / `planned_comment_gap_not_realized` 保留 code
  但仅在 `required` 且**确实为空**（`!findable`）时发，即真正的「计划了但没写」。

### 3. AI 判官裁决落库（消除观测盲区）

`ContentPackage` 新增 `claimJudgments?: ClaimJudgment[]`，组包时从 draft 复制。
这不改变任何判定行为，只让判官的工作可审计 —— 修复后即可回答「67 例
`sensitive_claim_without_evidence` 里判官覆盖了多少、判了多少 unsupported」，
这是后续决定要不要扩大判官覆盖面的前提。

配套：落库后用真实生成验证判官确实在产出裁决（当前无法证明，只能证明它没失败）。

### 4. 前端标签同步

`validation-labels.ts` 补 `unverifiable_by_lexical_match` 相关措辞；确认合并后的
message 在结论卡里仍可读。

  `comment_network_*` / `knowledge_backed_claim_unrecorded` /
