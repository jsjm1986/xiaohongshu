# 80 个生成参数的有效性治理 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: 使用 superpowers:subagent-driven-development 逐任务实现本计划。步骤用 checkbox（`- [x]`）跟踪。

**Goal:** 让用户在生成前填写的参数「填了就真的算数，不算数的要说出来」。当前 80 个参数里有一批在预设区间内不可分辨、被开关短路、或只有提示词没有约束，而 UI 上它们和真正硬生效的参数长得一模一样。本计划按证据分四类分别处理，不做「给每个滑杆加校验器」这种一刀切。

**背景（100% 代码实证，非推断）：** 参数只有三条到达产物的路径，且是互斥设计（`parameters.ts:425-429` 注释写明真源约定）：

1. **derive** — planning/engine 读值算出结构量，进 `orchestrationPlan`
2. **prompt** — `explicitBehavior()`（`parameters.ts:745`）生成一句中文，经 `COMMENT_STAGE_BY_ID`（`parameters.ts:430-458`）分侧注入
3. **VALIDATE** — `content.ts` 校验产物，违反即 issue → 触发 repair

其中关键事实：`stagedCommonUser`（唯一携带全量参数指令的载体，`prompt.ts:729`）**只到 2 个阶段** — `buildStagedCorePrompt`(737) 和 `buildStagedLedgerPrompt`(1354)。评论 8 个阶段在按侧隔离改造后只收 `commentStageInstructions(report, "reader"|"answer")`，所以 `commentStage` 表就是评论阶段的准入名单；表外的参数不进评论提示词。

**运行时扫描证据（固定种子，唯一变量为滑杆值，经真实 `planTopicOrchestrations`）：**

| 滑杆 | 实测 | 判定 |
|---|---|---|
| `question_compression` | 0→34字 / 50→25 / 78→20 / 100→16 | 连续可用 |
| `comment_constraint_density` | <35→0 / 35–69→1 / ≥70→2 约束 | 3 档可用 |
| `comment_expansion` | 0→3线程 / 25–70→4 / ≥75→5 | 3 档（受 min/max=3/5 限制） |
| `comment_conversation_rate` | growth=ON: 0→[0,1] … 100→[4,5]；**growth=OFF 恒 [0,0]** | 被开关短路 |
| `comment_role_diversity` | 0–39→stance 1 / 40–69→2 / **≥70→3 后完全不变**；distinctRole 恒 3 | **预设区间内是常量** |

`comment_role_diversity` 三处阈值在 `planning.ts:1475`(`>=75`/`>=40`)、`1591`(`>=40`)、`1592`(`>=70`/`>=35`)，而 10 个预设取值全在 75–95（`parameters.ts:513-610`），26 篇生产数据 100% 落在死区，75 与 100 产出逐字相同的计划。

**Architecture:** agent-core 是唯一事实源，API 只做投影（`apps/api/src/generation-parameters.ts:16-38`），web 不直接引 registry。因此「哪些参数当前无效」必须在 agent-core 计算、经 API 投影字段下发，不能在前端硬编码。

**Tech Stack:** TypeScript strict、vitest（agent-core `npx vitest run`，**不是** `node --test`）。实现落在 `/Users/a1234/Desktop/开发项目/小红书创作/文案/content-agent`。

## Global Constraints

- **digest 会失效**：`PARAMETER_POLICY_DIGEST`（`parameters.ts:1184`）哈希了 `registry + presets + styleProfiles + defaults`。阶段 1/2/4 任一改动 registry 或预设值都会移动它，而 `validateReleaseContract`（`apps/api/src/research.service.ts:728-738`）会对不上就抛 `发布清单绑定的运行合同已经过期`。**每个改 registry 的阶段收尾都必须记录：既有 active release 需重新激活。**
- **不新增会误报的 error**：`comment_conversation_rate` 绝不加校验器 —— 开关关闭时 `multiTurnTarget` 恒 `[0,0]`，加校验必然假阳性，`content.ts:1202-1206` 的 P2-11 注释正是在防这个。
- **必须保持绿的既有断言**：`test/cref-validation-p4.test.ts:384-387` 四条 `comment_surface_roles_flat` 断言（其 `validationConfig` 用 registry 默认值 85）；`test/planning.test.ts:392-410` 的 roleDiversity 0 vs 100 对比。
- 基线：agent-core **282 passed / 20 files**，`npx tsc --noEmit` 干净。每阶段结束都要回到这个状态或更高。
- 阈值调整只动确定性推导层，不改 JSON schema，因此 `PROMPT_CONTRACT_DIGEST` 不动。
- 无新依赖。面向用户文案用简体中文。
- 每阶段独立可验证、独立可回滚；按 1→2→3→4 顺序，前一阶段绿了再进下一阶段。

## 四类问题与对应处置

| 类 | 参数 | 症状（实证） | 处置 |
|---|---|---|---|
| A 死区 | `comment_role_diversity` | ≥70 后行为恒定，预设全在 75–95 | 阶段 1 重铺阈值 |
| B 短路 | `comment_conversation_rate` | 三处读取正确，但全在 `commentMultiTurnGrowthEnabled`(默认 false) 门后 | 阶段 2 空转可见化（**不加校验**） |
| C 名实不符 | `evidence_strictness`、`boundary_visibility` 等 8 个 | 无任何代码消费，仅一句提示词；前两个却标 `normative_boundary` | 阶段 4 名实对齐 |
| D 有意零路径 | 20 个 `*_diagnostic_*` | 只给 `diagnosticReports()` 排序，`prompt.ts:592` 显式剔除出模型契约 | 阶段 2 顺带标注，不改行为 |

C 类完整清单（无 derive、无 VALIDATE，仅提示词）：`state_information_strength`、`body_completeness`、`redundancy_tolerance`、`evidence_strictness`、`boundary_visibility`、`evidence_requirements`、`information_priorities`、`thread_style`。另有 `information_boundaries`(`parameters.ts:757`) 与 `comment_false_closure_guard`(`parameters.ts:801`) 的 `explicitBehavior` 返回**固定字符串，完全不随值变化**。

## 阶段 2：空转可见化（B + D 类）

**目标：** 不改任何生成行为，只让「这个滑杆当前不生效」变成结构化事实下发到 UI。风险最低、直接回答用户「填了这么多参数到底有没有用」。

- [x] 2.1 在 `types.ts` 的 `ParameterImpactTrace` 增加可选字段 `inertReason?: string`（当前值不生效的原因，中文一句）。**可选**以保持历史快照可读。
- [x] 2.2 在 `parameters.ts` 新增纯函数 `inertReasonFor(definition, config): string | undefined`，只覆盖能从 config 确定性判定的情形：
  - `comment_conversation_rate` / `comment_multi_turn_growth` 相关：`config.content.commentMultiTurnGrowthEnabled !== true` → 「多轮生长开关关闭，本滑杆当前不影响产出」
  - `comment_conversation_rate`：`config.content.followUpDepth <= 0` → 同类说明
  - `comment_expansion`：`commentThreadMax - commentThreadMin === 0` → 「线程上下限相同，展开力度无可调空间」
  - `*_diagnostic_*`：恒定返回「仅控制人工检查显示顺序，不进入模型与校验」
- [x] 2.3 在 `compileGenerationParameters`（`parameters.ts:1040-1060`）构造 trace 时填入 `inertReason`。
- [x] 2.4 让 `explicitBehavior` 对 inert 参数**不再产出指令文本**（避免给模型一句它无法执行的话）；`comment_conversation_rate` 在 growth 关闭时尤其如此。
- [x] 2.5 API 投影：`apps/api/src/generation-parameters.ts:16-38` 增加 `inertReason` 字段透出（保持「registry 与默认值归 agent-core」的既有注释约定）。
- [x] 2.6 写测试：growth=false 时 `comment_conversation_rate` 的 trace 有 `inertReason` 且 `behaviorInstructions` 为空；growth=true 时 `inertReason` 为 undefined 且指令回归。
- [x] 2.7 `npx vitest run` + `npx tsc --noEmit`；再跑 `apps/api` 测试（**注意既有 3 个失败是 main 上就红的基线，且 api 测试强顺序依赖，必须整文件跑**）。
